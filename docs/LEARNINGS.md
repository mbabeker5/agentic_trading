# Learnings register

Confirmed learnings only, one line each, dated, newest first. A learning is confirmed when it has been observed at least once in the live paper run or proven by a test, and it has changed something (a rule, a check, a doc). Proposals live in the journal until then.

Format: `YYYY-MM-DD | area | what we learned | what changed (commit)`

- 2026-09-10 | gateway | "Unrecognized Username or Password" after the nightly restart does not mean the password is wrong, because no password is typed on that path. The 02:00 restart resumes the previous session from a token file (`-Drestart=`) and the IBC log for that night contains no "Setting password" line at all: Gateway showed "Re-login is required", IBC clicked the button, which is the only thing its handler does, and IBKR refused the stale token. The same credentials file logged in at 11:27:57 and 13:49:46 the same day and the same restart worked at 02:00:08 the day before, so the message named the one thing that was fine. IBC 3.24.2 has no handler for that dialog and stops dead on it, the upstream repository was archived on 2026-09-01, and the pull request that would have handled it was rejected, so nothing is coming from there. | A ninth watchdog check, `gateway_login`, reads the refusal out of the newest IBC log, compares it with the newest completed login and earns one stop and start at any hour, which is the workaround IBC's own maintainer recommends. Shipped as `7a71971`, closes backlog item 32
- 2026-09-10 | operations | Every safety net in this project runs on the machine it is watching, so when the machine stops they all stop together and none of them notices. Between about 05:00 and 11:26 this Mac ran nothing: the watchdog missed 28 runs, the dead man's handle about 23, the recorder its first 25 slots, the 09:00 pre-flight left no verdict and no line in its own launchd log, and the loop wrote nothing until 11:26:04. Everything resumed inside the same minute, on no scheduled minute, which is launchd firing a backlog rather than a program recovering. Third trading day, third lost morning, and the cause was the machine rather than the Gateway on all three. | Backlog item 30: a watcher on the Mac Mini that reads `output/heartbeat` over SSH and alerts when it stops moving during market hours, since it is the only device that is not the one being watched. Proposal 2 in journal/2026-09-10.md
- 2026-09-10 | alerts | The alert log tells a Mac with no network apart from a Mac that has stopped, for free and to the minute. Jobs on a networked-but-offline Mac still run, so alerts are still written and fail on the Slack leg with `[Errno 8] nodename nor servname provided, or not known`; a Mac that is asleep or stopped writes nothing at all, not even a failed alert. Today's 05:00 to 11:26 gap holds neither kind, and the 12:55 to 13:48 window holds seven failed ones, which dated and classified both outages out of a file the project already writes. | Nothing to change in the code. Written into the diagnosis order in docs/OPERATIONS.md and used to date both of today's outages in journal/2026-09-10.md
- 2026-09-10 | reconcile | An account read of exactly 0.00 passes reconciliation as a match. At 12:55:06 the tick log recorded "Account DUT077572: worth 0.00, 0 positions and 0 working orders" with no error note at all, then "Reconciliation: everything matched" on the next line; every healthy tick that day read 1,000,604.32. Both zeroes fell on the minutes the network was failing, so a zero is a failed read wearing the costume of a fact, and it is invisible exactly when it matters, because a book holding nothing matches a broker showing nothing. | Backlog item 29: a zero equity read on a funded account is "the broker could not be read", the branch that already exists and already halts nobody, rather than a number the books are compared against
- 2026-09-10 | watchdog | A restart is only ever as good as the network under it, and the watchdog had no way to ask. At 13:00:04 `ib_answers` correctly failed while the port was still open and `ib_connect` still worked, so the watchdog stopped a Gateway that was answering; the replacement showed "connection error, will retry" for 29 minutes because there was no network to log in over, and the new fifteen minute rule restarted it a second time at 13:20 to the same effect. The port was shut from 13:05 to 13:50 as a direct result of the repair. Both restarts reported "restart did not take", which is the machinery working correctly on a question it should never have been asked. | Confirms backlog item 21 on the same day it was reprioritised: resolve IBKR's host name before any restart rule blames the Gateway, and skip the restart when that fails. Proposal 4 in journal/2026-09-10.md
- 2026-09-10 | loop | Book C cannot pick anything, and the reason is a file name rather than the market. `shortlist_path()` at agent/loop.py line 1209 builds `insider_shortlist_<the day it runs>.json`, and the pick reads the same name for the day it picks, so the 16:30 sweep that the strategy file describes as parsing "the day's filings for tomorrow morning" writes a file tomorrow's pick will never look for. - 2026-09-10 | gateway | The nightly 2 AM restart can be refused, and IBC stops dead when it is. At 02:00:06 IBC clicked "Re-login" and at 02:00:07 hit a dialog entitled "Unrecognized Username or Password", which is the last line in that day's IBC log. The Gateway sat with a credentials dialog on screen, its process id changed on its own by 03:00, and the API port stayed shut until it was restarted at 11:26. Nothing in the project reads IBC's dialog titles, so the watchdog reported a shut port for eight and a half hours without ever reporting the reason sitting in a log file next to it. | Backlog item 32: the watchdog reads the tail of the current IBC log when the port is shut and puts the last dialog title in the alert, so a credentials failure never again looks like a hang. Shipped the same evening as `7a71971`, and it acts on the refusal rather than only naming it
- 2026-09-10 | preflight | A pre-flight that cannot reach Gateway can end without writing anything at all, and a missing verdict was indistinguishable from a passing one. Today's 09:00 run left neither `output/preflight_2026-09-10.json` nor `output/NO_TRADE_TODAY`, so when Gateway came back at 11:27 nothing told the loop to stay out. Nothing in `agent/loop.py` had ever read a verdict file, so the contract "no pre-flight pass, no trade" was written down in three places and enforced in none. Only dry run mode kept the day safe, and mode is not the contract. | The pre-flight now guards every check and writes its verdict from a `finally` block, so a run that throws or is killed still leaves a fail on disk with `NO_TRADE_TODAY` and an alert (`dc8d22d`). The loop refuses entries, exits untouched, when today's verdict is missing, unreadable or not `pass`, and says so once per book per day (`6f67f0d`)
- 2026-09-10 | watchdog | A patience with no clock on it is not patience, it is a rule that never fires. The refusal to restart a Gateway whose process is alive but whose port is shut is right for the first few minutes and wrong after that, and it cost the mornings of both 2026-09-09 and 2026-09-10, over eight hours each. Stopping first is what removes the risk the refusal was guarding against, because `agent/stop_gateway.sh` kills the process, so there can never be two Gateways. | After 15 minutes of a shut port on a live process, with the market open or opening inside 90 minutes, the watchdog now stops Gateway and starts it again, once per outage, still silent between 01:45 and 02:30 and still never on error 10197. An unproved attempt on this path is recorded anyway, or a rule that fires every wake up would restart Gateway every five minutes. A verified restart now says so too (`95aede6`)
- 2026-09-09 | watchdog | The watchdog will not restart a Gateway whose process is up but whose port is shut, and there is no time limit on that patience. `_may_restart` only allows a port failure to trigger a restart when no Gateway process is running at all, on the reasoning that a shut port on a live process may just be a slow start. Today that process was wedged from 03:01 to 12:20 and the watchdog alerted eleven times without one repair attempt, 8 h 20 min of the trading day. The one check allowed to stop and restart a wedged Gateway, `ib_answers`, has to connect through the port to notice anything, so it was blind to it. | Backlog item 23: allow a stop-then-start once the port has been shut for a bounded time.
